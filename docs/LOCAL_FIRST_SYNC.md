# Chat Connect / MUSCAL — Local-First Synchronization Engine

## 1. Local-First Philosophy
Chat Connect adheres strictly to the **Local-First Software principles**:
- The primary copy of data resides on the user's local device in IndexedDB.
- Network availability is treated as an opportunistic enhancement, not a prerequisite for user interaction.
- The UI never blocks or displays spinners waiting for server or peer responses; messages are immediately rendered in a `queued` state and asynchronously dispatched.

---

## 2. Idempotency & Conflict-Free Processing

### Deterministic Sync Hash
Every message generated by `ConversationService` receives a cryptographic idempotency token (`syncHash`):
```typescript
syncHash = SHA256(`${conversationId}:${senderId}:${createdAt}:${content}`);
```
When an incoming message envelope arrives:
1. `MessageRepository.getByIdempotency(id, syncHash)` performs a dual-lookup.
2. If an identical message exists, the repository merges rather than creates a new record.
3. If lifecycle status conflicts occur:
   - Status transitions strictly respect priority ordering:
     $$\text{queued} < \text{sent} < \text{delivered} < \text{read}$$
   - State cannot regress: a message marked `delivered` will never revert to `sent` or `queued`.

---

## 3. Outbox Queue & Offline Resilience

When offline or disconnected from peers:
1. Messages are written to IndexedDB with `status: 'queued'`.
2. A corresponding record is written to `SyncStateRepository` with `status: 'pending'`.
3. When `TransportAdapter` fires an `ONLINE` or `CONNECTED` event:
   - `SyncService.push()` wakes up automatically.
   - Pending outbox items are serialized into signed transport envelopes and transmitted across the mesh.
   - On peer acknowledgment, the message transitions to `sent` and the outbox item is marked completed.

---

## 4. Attachment Deduplication & Binary Storage

Files, images, voice clips, and documents are stored in a dedicated IndexedDB store (`attachments`):
- **Deduplication**: The entire binary file is hashed using SHA-256 (`att_h_<hash>`). If the same file is sent across multiple conversations or by multiple participants, only a single binary Blob is retained in local storage.
- **Reference Counting**: Multiple messages point to the same attachment record, drastically reducing storage footprint on mobile browsers.
